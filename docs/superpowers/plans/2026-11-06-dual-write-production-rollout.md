## Proposed design and scope

- Confirmed by the user: strict dual writes. Upload success requires both verified originals and durable scheduling of required processing. If a response claims a thumbnail already exists, both required copies must also be verified; otherwise thumbnail status remains pending. If B2 fails after GCS succeeds, return a retryable failure and retain durable intent. Upload acceptance and completion of all asynchronous artifacts are separate observable states.
- Alternative considered and rejected for this milestone: accept GCS and mirror asynchronously using the existing Blossom mirror approach. This preserves upload availability but permits successful uploads without a B2 copy and has different completion/backlog guarantees. The user selected strict dual success.
- Extend the existing versioned finalization contract, not the old hash-only transcoder request. A 2xx acknowledgement means persisted work; it never means transcoding, moderation or delivery approval has completed. Upload acknowledgement requires both originals and a committed producer outbox event; it does not wait for receiver acknowledgement. Consumer outages buffer work durably. Asynchronous artifact status remains pending until its required copies are verified.
- Prefer extending the existing Blossom processing deployment with versioned intake and durable jobs. Task 1 must first prove it can own acknowledged work across restarts and retry delivery to processors. The existing Cloud Tasks status-callback queue is not a processing queue. Add a small GKE intake/worker service only if reuse cannot meet the ownership, runtime or isolation requirements; do not move or rewrite the transcoder. Runtime placement is an explicit Task 1 decision.
- All active new-media upload paths, originals and newly generated thumbnails, HLS/renditions, transcripts/subtitles, and extracted audio follow the recorded dual policy. Audit additional artifacts and alternative writers before activation. Build and test B2-only source processing in this milestone; historical migration and the default playback switch remain separate activation steps.
- Retain GCS originals, public URLs, current playback routing and existing approved-only B2 delivery behavior. Raw B2 writes do not create approved-replica readiness records.

## Admission policy and activation interlock

**Preferred design, to specify in Task 1 and implement in Task 3B:** one environment-scoped policy record with mode, monotonic epoch, destination-map identity and compatible release/configuration identity. Keep a separate append-only change audit (actor, reason, prior/new epoch). Use the existing restricted operational workflow; no public policy-management endpoint.

- Resolve and persist policy on the authoritative database with the creation of a new upload intent, resumable admission or on-demand artifact job. Serialize policy updates with this short transaction so the policy commit defines the admission boundary. Do not hold database locks across provider I/O. Neither a stale cache nor a lagging read replica authorizes new admissions. Existing intents/sessions/jobs use their stored policy without reevaluating the current mode.
- Apply this to every active writer, not only uploader replicas. A service without direct database access must call the authenticated admission boundary. The artifact policy must preserve destinations already required for that media. Synthetic and production policy scopes are separate.
- Policy-read failure rejects new work with a tested retryable response, never a silent GCS fallback. Existing work continues only where its normal coordination and durable-state requirements can still be met. A DB outage is not repaired by changing an environment variable.
- Use a conditional policy update against the expected epoch; audit concurrent/stale operator writes. Configure exactly one authority: shared-policy mode or static deployment mode. In shared mode, `MEDIA_WRITE_PROVIDER` must not override the database or silently bootstrap missing production policy. Credentials/adapters for both providers remain loaded across admission changes.
- Promotion to dual requires recorded acceptance evidence for the exact writer, eraser, receiver and processor releases, schema and destination mapping. Incompatible config/release changes invalidate promotion eligibility. Coreconfig deployment checks cover every serving instance; workers reject unsupported job contracts without acknowledging completion. Test a missed/reverted processor deployment. This interlock is new work, not an existing platform feature or proof against arbitrary out-of-band changes.
- Transient receiver/processor unavailability is backlog, not contract incompatibility. It must not turn intake into a live fan-out dependency. Alert and apply measured backlog/admission limits; preserve producer outbox durability. B2-only production admission stays disabled until the separate cutover decision.

**Fallback:** if the policy/interlock implementation cannot meet these invariants in the intended scope, retain static configuration and the tested drained handover in Task 7. Do not build percentage cohorts to ship full dual.

## Global constraints

- Separate private raw-authority and approved-only delivery buckets. Verify exact account, name, ID, region, privacy, version/retention/lifecycle behavior and erasure capability privately; preserve existing buckets.
- No credential values in code, plans, commands printed to users or public artifacts. Use separate scoped workload secrets and existing approved provisioning processes.
- Full hashes and exact immutable provider versions; ETags are not content identity. Public descriptors retain canonical CDN/hash URLs.
- Every writer and eraser for a destination must share an enforced coordination boundary. Finalization after a write is too late to prevent resurrection.
- Raw uploads may await moderation; storing bytes grants no public visibility. Preserve authenticated ownership, moderation, quarantine, tombstones and permanent deletion intent.
- Preserve GCS sessions and pending work across deployment/provider changes. No rollback to a GCS-only binary after admitting B2 work.
- Expand schema first; test every binary/schema combination used during rollout and rollback. Contract/drop old fields only after all dependent binaries and pending work have drained.
- Implementation follows per-repo isolated worktrees, independent reviews, mapped reviewers and GitHub checks/approval. This planning document authorizes no production switches or credential changes.

## Review focus

1. Lost provider responses and partial dual success: retain intent and resolve exact versions without blind overwrite or automatic copying during erasure.
2. Deletion races and duplicate owners: no late write/derivative can resurrect media or bypass ownership policy.
3. Mixed deployments and old sessions: requests preserve provider/bucket mapping, tokens and contiguous offsets across replicas/restarts.
4. Consumer crashes and duplicate delivery: durable acknowledgement, bounded retries, fenced job ownership and idempotent artifact publication; computation can repeat after a crash.
5. Client saturation and large/malformed media: bounded resources, explicit 413/503 behavior, usable client recovery and observable failures.
6. Policy changes and outages: one recorded admission boundary, no downgrade of accepted strict-dual work, measured restoration for new uploads and visible backlog for existing ones.
